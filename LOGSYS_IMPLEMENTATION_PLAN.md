## 4. Phase 2 · Verify competing hypotheses and gate the explanation

**Timing** · Week 2. Survey objective 2. This is the central demo feature.

1. **Generate a small set of candidates.** Start with a supported shortlist such as DB connection pool exhaustion, CPU saturation and a bad rollout. Form candidates only for plausible service and fault-type pairs from retrieved evidence and the incident window. If no candidate has usable evidence, return insufficient evidence.
2. **Implement a deterministic verifier between retrieval and RCA in `Orchestrator.run()`.** Define, for each fault type, its expected local indicators, expected downstream symptoms, required coverage and potential refuters. Return a per-candidate score breakdown for temporal ordering, supported dependency path, independent corroboration, contradictory observations and missing prerequisites. Use explicit rules and fixed evaluation thresholds tuned on development fixtures. Positive scores are rank signals, not calibrated probabilities.
3. **Decide before generating text.** Require an incident-window primary indicator, a plausible order/path for propagation claims and a clear lead over the next candidate. Use decision states such as `supported`, `ambiguous` and `insufficient_evidence`, with reasons. Treat missing data as unknown. An adequately sampled normal connection-pool signal during the incident can refute an exhaustion hypothesis, while absent pool data cannot.
4. **Make citations machine-checkable.** Extend `RCAOutput` with additive fields for decision, candidate rankings, support/refutation IDs, missing signals and structured timeline events. Each statement the system displays as causal should come from an approved claim with attached IDs. Have the LLM summarize a bounded set of approved claims and validate returned references and their claim associations. Render deterministic claim text if the output fails validation or the provider is down. Preserve old chat history rendering.
5. **Adopt shadcn/ui in the existing React and Vite frontend.** Set up Tailwind CSS for shadcn/ui and share theme tokens for typography, spacing, surfaces, borders and semantic status colors. Migrate the active session sidebar, upload controls and query composer to shared Button, Input or Textarea, and Alert Dialog components. Use Tabs for Evidence, Timeline, Graph and Agent Trace, Card and Badge for hypotheses and decision states, and Alert and Skeleton for errors, empty states and in-progress analysis. Keep the existing drag-and-drop and graph behavior within those views.
6. **Make the evidence easy to scan and navigate.** Put the diagnosis decision and leading hypotheses first. Link “Supports”, “Contradicts” and “Missing” to the relevant evidence or timeline entry. Label Pinecone similarity as retrieval relevance and display decision strength separately. Use color alongside readable status labels. Verify keyboard navigation, visible focus, contrast and the upload-to-evidence flow on both narrow and desktop screens.

**Exit criteria.** With corroborating telemetry, DB pool exhaustion ranks ahead of a later CPU spike with a traceable evidence chain. A case variant with strong opposing telemetry is reflected in the matching candidate’s score and decision. Removing decisive observations yields ambiguity or insufficient evidence on the designated stress fixture. Every causal claim shown links to evidence from the requested session.
